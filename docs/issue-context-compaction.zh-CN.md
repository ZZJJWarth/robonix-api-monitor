# [RFC] 用可选的本地 monitor 先验证上下文压缩，再考虑进入系统层

## 问题

Pilot 每个规划步都会重发完整历史。执行包装、重复的兜底记录、被覆盖的快照以及重复的
目录/手册文本不断累积，prompt token 随步数近似二次增长。在一个较长的物理机器人任务中，
单个请求达到 **400 条消息、约 12 万 prompt token**，整个任务消耗 **3.93M token**。

长 prompt 还会与执行相互影响：provider 的流式超时和偶发空回复更容易出现。

## 提案

暂时不修改 Robonix。先用一个**外部、可选**的 monitor 做验证：

- monitor 是只监听回环地址的 OpenAI 兼容代理。Pilot 把 `VLM_BASE_URL` 指向它即可，
  除这个 URL 外不需要改动 Robonix 源码或清单。
- 它把每个请求/响应记录到本地，并可以选择在转发前压缩可识别的 Pilot 请求
  （`--compact-context`）。
- control 与 treatment 使用同一个代理，只切换压缩开关，因此 token 统计方式一致，
  变量只有一个。
- 如果社区 A/B 显示行为没有退化，再把压缩逻辑落到 Robonix（Pilot 历史写回或系统层
  组件；具体位置是后续讨论项）。

monitor、部署 README 和 A/B 协议都在本仓库：`README.md`。

## 压缩做了什么

对可识别的 Pilot 请求，压缩把执行后缀折叠成一个确定性的 **execution memory** 块：

- 保留 system prompt、用户/任务文本、当前能力目录、能力手册、任务记录、最新实时快照、
  当前任务板，以及空槽证据。
- 保留每一次调用和每一条结果作为有序证据，包括失败和同一调用的重复反馈。
- 去掉重复的传输包装和叙述、被覆盖的任务记录版本、被覆盖的 dispatch 记录，以及已被
  更新权威快照取代的旧快照。
- **不额外调用模型**，不改写指令，也不添加任务答案。相同输入得到相同输出。

400 条消息的实测形态是 400 → 9 条。这是结构化合并，不是删掉 98% 的信息：保留的消息
包括能力目录（约 26k 字符）、两份能力手册、一个紧凑的 execution-memory 块（约 93k
字符）、任务记录、实时快照和任务板。

## 初步证据与局限

以下数据来自内部的一个物理机器人场景和**一个模型**（DeepSeek flash），
应视为需要社区验证的假设。

- 端到端任务：未压缩 3,927,758 total token，压缩后 1,062,624（**-73%**）。
  墙钟时间也下降，但不同 run 的行为差异使该对比噪声较大。
- 回放已记录的决策点：prompt token 下降约 **64%**。
- 输出质量回放，每种条件 10 次：未压缩 prompt 在一个决策点 8/10 通过、另一个 10/10；
  压缩 prompt 两个决策点都是 10/10。仅有的空回复都出现在 400 条消息的未压缩 prompt 上。
  所有非空输出都是严格 JSON，带有效 RTDL envelope，且只使用 prompt 中存在的 capability。
- 任务级样本太少（干净对比中压缩 2 次、未压缩 1 次），且受到 provider 降速和超时影响。

这**不能**证明：其他本体、其他模型/供应商、不同证据结构的任务上没有退化；统计意义上的
非劣性；跨 provider 的 prompt cache 行为。

## 如何测试

使用 `README.md` 中的 A/B 协议：

- 两臂使用相同模型、任务集、复位流程和外部成功判据。
- 至少 3 个不同任务，每臂至少 10 次配对运行，两臂交替执行。
- 比较任务成功率、无效输出率、请求数、prompt/completion/total token 和墙钟时间。
- 建议的非劣门槛：成功率 95% 置信区间下界不低于 control 超过 5 个百分点；
  无效输出率上界不高于 control 超过 5 个百分点；prompt token 中位数至少下降 30%。

报告时请附任务、本体、模型/供应商、运行次数、置信区间，以及超时/空回复的观察。
负面结果同样有价值：monitor 的目的就是在压缩进入系统层之前找出它不安全的场景。

## 风险

- 不同 provider 的 prompt-cache 行为不同。历史重排或缩短可能减少可复用的缓存前缀，
  而 token 总数看不出这一点。
- 如果历史里没有更新的权威快照，压缩可能保留过期证据。当前实现保留最新快照并记录
  版本边界，但领域语义仍然重要。
- 评测偏差：模型自述不能作为成功判据，不同 run 的任务难度也会波动。
- 很长的 prompt 可能导致空回复或流超时；A/B 必须把它们计为失败，而不是丢弃。
- 压缩目前针对 Pilot 的 RTDL 历史格式调优。非 Pilot 请求原样转发，无法识别的请求
  不会被压缩。

## 本提案不包含

- 对 Robonix、Pilot prompt、capability 或 contract 的任何修改。
- “压缩在所有场景都安全”的结论。
- 生产网关或托管服务。monitor 是本地测试工具，只监听 `127.0.0.1`，prompt 存在本地，
  记录不得公开。

## 请求

请至少用一台与你的本体和模型匹配的环境跑一次 A/B，并贴出汇总表和验收门槛结论。
如果多个独立环境都显示非劣行为，我们可以用这些结果作为依据，提议把压缩逻辑落到上游。
